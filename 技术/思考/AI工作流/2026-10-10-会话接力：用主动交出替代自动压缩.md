# 别等 AI 把自己"压缩"了：从会话接力聊到 AI 工作的 harness

用 AI 写代码久了，大概都碰到过这种时刻。

一个会话从早上干到下午，聊了架构，定了规矩，派出去好几个子任务，你也零零碎碎交代了不少"这里别这么做""那个以后再说"。然后屏幕上跳出一行小字：上下文快满了，正在自动压缩。

压完之后它照样干活，语气也一样自信。可没过几轮你就会发现不对劲：上午刚说好的约定，它又犯了；问它某件事做到哪了，它给你一句"正在推进 X"，再问细节就开始含糊；后台还跑着一个子任务，它压根不记得自己派过。

这事我琢磨了一阵，最后想通了一点：**问题不在压缩算法够不够聪明，而在于压缩发生的时机，以及做决定的那一方。**

## 压缩为什么靠不住

自动压缩看的是长度，满了就压。它分不清哪句话是你随口一提，哪句话是你拍了板、以后每次都要守的。它也不知道"后台还有个任务没收"这种事，比前面几十轮讨论加起来都要紧。

更要命的是时机。压缩总是在上下文**最满**的时候触发，偏偏这时会话的状态是最差的：信息最杂，注意力最散。等于让一个熬了通宵的人，在最困的时候给自己写交接单。Claude Code 默认在上下文用到 95% 时才自动压缩（可以用环境变量 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` 调低），换算到 100 万 token 的窗口，就是大约 95 万 token 的时候。

后来我去了解了一下 Claude Code 的自动压缩具体怎么做，大致是三步：

- 先做一轮便宜的清理，把早期大段的工具输出（安装日志、搜索结果之类）清掉，只留最近的一部分（网上拆解的说法是约 4 万 token，官方文档没给具体数字）；
- 再把清理过的历史交给模型，按内置模板写一份结构化总结，替换掉原来的对话；
- 最后从盘上补回一些东西：项目的 CLAUDE.md 和长期记忆、git 状态，以及最近读过或改过的几个文件。

所以它对大局抓得其实不差：目标、改了哪些文件、定下的架构决策、下一步做什么，基本都能留住。容易丢的是另一类：

- **被否决过的方案。**第 10 轮说好"因为 A，不能用 B"，压缩后多半只剩"现在用的是 C"。到第 50 轮，它可能又把 B 提了出来。
- **偶发的细节。**很早以前某条命令报过一次的怪错误，基本会被当成噪声剪掉。
- **随口交代的约束。**比如"别动那个方法"，在写总结的一方看来，这可能只是个小细节。

这些恰好都是"重要但不显眼"的东西。总结写得再认真，决定什么重要的仍然是它，不是你。

那换个思路：**趁它还清醒，让它自己决定留什么。**

## 会话接力是什么

做法很朴素。在上下文还健康的时候主动叫停，让当前会话把该留的东西整理好、落到盘上；然后换一个干净的上下文，读这些材料接着干。

它和手动执行 `/compact` 不是一回事。`/compact` 的总结只活在当前会话里，`/clear` 或者关掉窗口就没了；接力文档落在盘上，新会话随时能读，用户也能打开改两笔。新会话也不会带着旧会话调试时的错误信息和废弃思路。

这个思路和官方的建议是对得上的。Anthropic 在 [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) 里讲长任务怎么管上下文，列了几种手段：压缩、清理旧的工具结果，以及让 agent 定期把笔记写到上下文之外、需要时再读回来，文中说后者"以很小的开销提供持久记忆"。Claude Code 的[最佳实践文档](https://code.claude.com/docs/en/best-practices)也建议在不相关的任务之间用 `/clear` 清空。会话接力就是把这两条接在一起：先把笔记落盘，再清空重来。

我管这个叫**会话接力**。起名时我特意避开了"交接"这个词，因为手头另一件事已经占用了它，是指把工作交给另一个人。会话接力不一样，是**同一个角色**换了个脑子继续跑。名字不分清楚，后面讨论会一直打架。

听起来很简单，真做起来，有几个地方不想清楚就会翻车。

## 第一个坑：什么都往接力文档里塞

一开始的直觉是：让旧会话写一份详尽的总结，越全越好。

这条路走不通。总结越写越长，长到接手的人也要从头读一遍，那跟把上下文原样搬过去有什么区别？更糟的是，这份文档下次接力会被覆盖，里面那些真正重要的结论就跟着没了。

后来我把信息拆成两类：

- **长期知识**：规则怎么定的、架构为什么这么搭、用户拍过板的事、踩过的坑。这些东西**不该进接力文档**，应该回到它们本来的家，也就是项目文档、决策记录、规范文件，或者 AI 的长期记忆。
- **在手状态**：我是谁、目标是什么、做到哪一步、在跑什么、在等谁、下一步打算干嘛。**这些才写进接力文档。**

分完之后，接力文档一下子瘦到一页以内，能放链接就放链接，不抄原文。

长期知识放对地方还有个附带的好处。像 CLAUDE.md 这类项目规范，压缩之后会被重新加载，写在里面的规矩不怕被压掉（官方文档原话是 "CLAUDE.md instructions survive compaction"）。那些"绝对不能违反"的约束，与其指望它记住，不如直接写进去。

我给自己定了个检验标准：**把接力文档删掉，项目的知识不应该少一点。**少掉的只能是"手头这一段在干什么"。做得到，说明分对了。

## 第二个坑：只写总结，不收尾

会话一关，它派出去的后台任务、子代理、监听器都不会跟着走。新会话完全不知道这些东西的存在，它们要么白跑，要么跑完了结果没人收。

所以交出不只是写一份文档，**交出之前得先把手头收拾干净**：

- 快跑完的，等它跑完，把结论落盘；
- 等不了的，停掉，写清楚停在哪、产出在哪、怎么续；
- 写到一半的文件，要么写完，要么标明"没写完，还缺什么"；
- 别的会话要是会给它发消息，提前打声招呼："我要换人了，新的会联系你。"

说白了，就是先把桌面收拾干净，再把钥匙交出去。

## 第三个坑：接手方太老实

接力文档是旧会话某一刻的快照。等新会话读到的时候，世界可能已经变了：当时"在跑"的任务也许跑完了，"在等"的回复也许已经到了。

如果新会话照着文档一条条往下执行，就会在已经过期的信息上干活。所以接手时要多做一步：**先核对，再动手。**

文档说在跑的，去看看是不是还在跑；说在等的，去看看是不是已经到了。对不上就以现状为准，并且告诉用户。

最后再用几句话复述一遍：我是谁，目标是什么，做到哪了，下一步干嘛，哪里跟文档对不上。这一步几乎不花什么成本，用户扫一眼就知道它接没接对。

## 第四个坑，也是我觉得最关键的：用户嫌麻烦

前面三条都对，但只要每次接力用户都得忙活半天，这套东西就坚持不下去。机制再漂亮，没人用也是白搭。

我的标准是：**用户只做会话做不了的事。**

在支持清空上下文的工具里（比如 `/clear` 这类命令），同一个窗口就能接力，用户只需要三步：

1. 说一句"准备接力"；
2. 敲 `/clear`；
3. 说一句"接手"。

第 2 步只能用户来做，因为会话没法对自己执行斜杠命令。我也想过让会话自己清空、自己接上，查下来确实做不到。其余的判断、收尾、自检、核对，全交给会话。

### 别让用户报路径

这里有个特别具体的痛点：接手时到底读哪份文档？要是每次都得告诉它"去读某某目录下的某某文件"，三次之后我就不想用了。

解决办法是让文档自己能被认出来：

- 放在**固定的目录**，按角色起名；
- 第二行写一个**状态**：`待接手` 或 `已接手`。交出时写前者，接手确认后改成后者，下次就不会接错；
- 加一小节**识别线索**：角色名和别名、一句话说清在忙什么、工作范围、这次是怎么交出的。

### 有好几份候选怎么办

同时开着好几个角色的时候，可能会有好几份"待接手"。我的想法是：**别搞死板匹配，让它综合判断。**

它能用的信号大概有这几种：

- **新鲜度**，这是最强的信号。同一个窗口接力，旧会话通常几分钟前才写完文档，明显比别的都新。
- **用户的话。**用户说"接手"时要是顺口带了角色名或者主题词，拿去跟识别线索对一对。
- **排除法。**如果某个角色还有一个活着的会话在担任，那份文档就不是给你的。
- **环境。**当前的工作目录、手上的范围对不对得上。

判断完会有三种结果：

- **有一份明显胜出：**直接接手，同时**把判断依据说出来**，比如"我接的是 A，因为它三分钟前刚写好，不对请告诉我"。
- **实在分不出来：**把候选列出来让用户挑。
- **一份都没有：**直说没找到，别猜。

这里我最满意的一点是：**线索是用来帮它判断的，不是一条必须严格匹配的规则。**它可以挺有把握地自己拿主意，但会把理由摆出来，你一眼就能纠正。比起"必须精确匹配某个字段"，这样灵活得多，也不容易因为一个字没对上就卡住。

## 最后，几条原则

琢磨完这一圈，我留下了这几条：

- **主动优于被动。**趁上下文还健康时交出，别等它被压缩。
- **知识和状态分开放。**长期知识回长期的位置，接力文档只放手头状态。
- **先收尾，再总结。**在跑的事比漂亮的总结更要紧。
- **先核对，再干活。**接手先看现状，然后复述，最后开工。
- **用户只做会话做不了的事。**两三句话加一条命令，就够了。
- **能自己认就自己认，但要说依据。**
- **可靠性措施不能比它防的损失还贵。**接力文档一页以内，不写进度日志，不搞冗余备份。

## 再往上一层：这其实是 harness 的问题

写到这里我意识到，会话接力只是表面。底下真正的问题，是我们怎么给 AI 搭一个能长期干活的工作环境。现在大家管这个叫 harness，可以理解成套在模型外面的那一圈东西：规范、工具、记忆、流程、检查。

用得越久，我越觉得**模型的能力决定了上限，harness 决定了它在长期工作里能稳定发挥出多少。**一个很强的模型，放在一个乱糟糟的环境里，照样会忘事、会重复犯错、会把半成品当成品交出来。

从会话接力这件事出发，我对 harness 有几点体会。

### 一、上下文是一种要花钱的资源

一开始我把上下文当成"聊天记录"，后来才发现它更像内存：容量有限、读写都要成本，而且越满越慢、越容易出错。

想通这一点，很多做法就顺了：

- 主会话应该只装**统筹需要的东西**，比如目标、边界、决定、进度。细节交给子任务去读、去做，回来只交一份摘要。
- 子任务要设计成**小而能独立验证的**：几分钟跑完，失败了损失也小，重来的代价也低。
- 读大文件、看长日志这种事，能用搜索和计数解决，就别整份读进来。

说到底就是给上下文做预算，把它花在判断上，而不是花在搬运信息上。

### 二、知识要住在文件里，不能住在会话里

这是我从接力这件事里得到的最大收获，而且它远不止适用于接力。

人类团队里有个老问题叫"知识在人脑子里"：某个人一走，他知道的东西就跟着走了。AI 的情况更极端，**每个会话都注定会"离职"**，上下文一满、窗口一关，它就没了。

所以 harness 里一个很重要的原则是：**凡是以后还用得上的东西，都要落到文件里。**用户的决定写进决策记录；设计意图写进设计文档；踩过的坑写进规范；手头进度写进接力文档。

会话应该是随时可以替换的，知识不应该。做到这一点之后，换会话、开新任务、让别的 AI 接手，都会变得很便宜。

### 三、规矩写成检查，别只写成文字

我以前也给 AI 写过很长的规范文档，效果一般。规矩写得再清楚，它也有可能漏读、忘读，或者读了没照做。

后来的做法是：**能用脚本检查的规矩，就写成检查。**

- "测试一条没跑却显示全部通过"这种事，让测试工具在 0 条用例时直接判失败；
- "某个旧名字不准再出现"，就写一个扫描，出现就报错；
- "提交前必须测试通过"，就把测试塞进提交流程里，不过不让提交。

文字规范负责讲清楚"为什么"，检查负责保证"做到了"。两样都要有，但真正兜底的是后者。

### 四、把人的精力留给判断

我自己的角色，在这套东西里慢慢变得很清楚：**我只做 AI 做不了、或者不该替我做的事。**

AI 做不了的，比如敲一个它没法自己执行的命令。不该替我做的，比如设计上的取舍、规则上的偏离、范围上的变化，这些得我拍板。

其他的事，像提交节奏、工程细节、默认值怎么取，我会明确告诉 AI："你自己定，记下来就行，别等我。"因为我经常不在，要是每个小决定都卡着等我，它就只能干等。

所以 harness 不光要约束 AI，**也要替人减负**。一个好的流程，应该让人感觉越用越轻松，而不是越用越累。

### 五、可靠，但别贵过它要防的损失

我的 token 额度是有上限的，任务随时可能断掉，接口也偶尔会抽风。这让我对"可靠性"有了更实际的看法。

一开始很容易往重了做：频繁存档、详细日志、多份备份。但这些都要花钱。最后定下来的原则是：**中断时损失控制在"一小段工作"以内，就够了。**长任务按自然段落落盘，断了从断点接着做，落盘的就是产出本身，不额外加一层进度汇报。

可靠性措施本身也是成本。它不能比它要防的损失还贵。

### 六、harness 是长出来的，不是设计出来的

最后一点体会是：这些东西没有一样是一开始就想好的。

会话接力是在一次次"压缩完它又忘了"之后才想出来的；"知识住在文件里"是在一次次重复交代之后才意识到的；"规矩写成检查"是在规范被无视了几次之后才转过来的。

所以我现在的习惯是：**每遇到一次摩擦，就停下来问一句，这里能不能改得更顺？**一个重复的手动步骤、一条没人检查的规矩、一笔浪费掉的额度、一个多余的常驻会话，都是信号。改动尽量小，说清楚省了什么，然后继续干活。

harness 不是一次搭好就完事的框架，它会跟着你的工作方式一起慢慢长出来。会话接力只是它长出来的其中一根枝。
